# 開発者ガイド

対象: 本リポジトリを引き継いで運用・改修する開発会社

---

## 1. セットアップ

```bash
npm install       # postinstall で prisma generate が走る
npm run dev       # http://localhost:3000（環境変数ゼロでデモモード）
npm test          # vitest 127件
npm run typecheck
```

PostgreSQL を使う場合:

```bash
cp .env.example .env.local   # DATABASE_URL を設定
npx prisma migrate dev --name init
npm run prisma:seed          # デモデータ
```

## 2. 必ず守るレイヤリング規約

詳細は `docs/ディレクトリ構成.md`。違反すると保守性が急速に劣化します。

1. `app/` はルーティングと表示のみ。ビジネスロジックは `modules/`
2. Prisma は `lib/store/prisma.ts` 以外から import しない
3. 外部 SDK / fetch は `modules/*/adapters/` と `modules/bitcoin/sources.ts` のみ
4. `modules/revenue/engine.ts` は純関数（他モジュールを import しない）
5. BTC 金額は文字列 + `lib/decimal.ts`。**number で加減算しない**
6. `tenantId` は必ず引数で明示的に渡す（Store インターフェースが強制）
7. Server Component は `lib/store` を直接呼ぶ。Client は `lib/client.ts` の `apiFetch`

## 3. よく行う変更のレシピ

### 画面を追加する

1. `src/app/(app)/<name>/page.tsx` を作成（認証は layout が担保）
2. ナビに載せる場合は `components/layout/Shell.tsx` の `USER_NAV` に追加
3. データ取得は Server Component から `modules/` を呼ぶ

### API を追加する

1. `src/app/api/<name>/route.ts` を作成
2. 必ず `handler()` で包み、`getSessionContext()` → 認可 → `zod` 検証 → 処理 → `audit()`
3. 変更系は `verifyCsrf(req)` を先頭で呼ぶ
4. レスポンスは `lib/api.ts` のヘルパーのみ使用

### DB スキーマを変更する

1. `prisma/schema.prisma` を編集（BTC 金額は `Decimal @db.Decimal(18, 8)`）
2. `npx prisma migrate dev --name <説明>`
3. `src/types/index.ts` のドメイン型を更新
4. `lib/store/types.ts` → `memory.ts` → `prisma.ts` の3点を揃える
   （memory を先に実装するとテストが書きやすい）

## 4. マイニングプロバイダーを追加する（最も重要な拡張点）

契約先の API 仕様書を入手したら:

1. `src/modules/provider/adapters/provider-a.ts` をコピーして新ファイルを作る
2. 3 箇所を実装する
   - `buildRequest()` — 認証方式・エンドポイント
   - `parseWorkers()` — レスポンス → `ProviderWorkerReading[]` への正規化
     （単位変換に注意: 本システムは **TH/s 統一**。`safeNumber` で必ず範囲検証する）
   - `healthCheck()` — 軽い疎通確認
3. `src/types/index.ts` の `ProviderKind` に種別を追加
4. `registry.ts` の `createAdapter()` に 1 行追加（switch が網羅チェックしてくれる）
5. API キーは環境変数（本番は Secrets Manager）に置き、DB には `credentialsRef`（参照名）のみ
6. テストを書く: 実 API のレスポンス例を fixture にして `parseWorkers` を検証

## 5. ウォレット（カストディ）を接続する

1. `src/modules/wallet/providers/custody.ts` を作成し `WalletProvider` を実装
   - `send()` は**冪等**であること（同じ idempotencyKey で 2 回呼ばれても送金は 1 回）
2. `modules/wallet/index.ts` の `getWalletProvider()` の `custody` 分岐で返す
3. `WALLET_PROVIDER_MODE=custody` で切替
4. ⚠ 秘密鍵をアプリ側に持たない。署名は必ずカストディ / HSM 側で行う

## 6. テスト方針

| 対象 | ファイル | 重点 |
|---|---|---|
| 収益計算 | `tests/revenue-engine.test.ts` | 既知値との一致・恒等式・境界 |
| 元帳 | `tests/ledger.test.ts` | 残高が消えない・二重計上しない |
| 出金リスク | `tests/withdrawal-risk.test.ts` | 検知シナリオ・承認者数 |
| アドレス | `tests/bitcoin-address.test.ts` | 公式テストベクタ・改ざん検出 |
| TOTP | `tests/totp.test.ts` | RFC 6238 ベクタ |
| テナント分離 | `tests/tenant-isolation.test.ts` | **他テナントの ID を知っていても見えない** |

新機能にも同じ水準を要求してください。特に金銭に触る変更は、失敗ケース（残高不足・重複・権限なし）のテストを必須とします。

## 7. デバッグのヒント

- デモデータを作り直したい: サーバー再起動（インメモリは起動時に再シード）
- 外部 API の疎通: `/admin/health` に breaker の状態と直近エラーが出る
- 監査ログ: `/admin/audit`。API の失敗も `result: FAILURE` で記録される
- SSE の確認: `curl -N http://localhost:3000/api/stream/dashboard`（要 Cookie）
