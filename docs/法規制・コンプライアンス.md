# 法規制・コンプライアンス上の確認事項

> ⚠ **本書は法的助言ではありません。** 技術者の視点で「弁護士・行政書士・監督官庁に必ず確認すべき論点」を
> 網羅的に整理したチェックリストです。事業開始前に、必ず暗号資産分野に精通した専門家のレビューを受けてください。

---

## 1. 最重要論点 — 「これは金融商品に該当しないか」

クラウドマイニングは、**設計次第で規制対象の金融商品と判断されうる**領域です。
ここを曖昧にしたまま販売すると、無登録営業として重大な法的リスクを負います。

### 1.1 判断を分ける要素

| 要素 | 規制リスクが**低い**方向 | 規制リスクが**高い**方向 |
|---|---|---|
| 提供物 | 「計算能力（ハッシュレート）の利用権」という役務 | 「利益の分配を受ける権利」という投資契約 |
| 収益の表示 | 変動する推定値として提示 | 確定利回り・元本保証をうたう |
| 収益の源泉 | ユーザーが選んだ設備の稼働結果 | 事業者の運用努力による分配 |
| 勧誘 | 仕組みとリスクの説明 | 「儲かる」「不労所得」などの投資勧誘 |
| 資金の扱い | 役務対価として受領 | 出資金をプールして運用 |
| 譲渡性 | 契約は非譲渡 | 契約が転売可能・二次市場がある |

**本システムの設計方針**: 左列（規制リスクが低い方向）に寄せてあります。
- 収益はすべて `推定` と明示し、保証表現を UI・API から排除
- 損益分岐点・感度分析を必ず表示し、損失可能性を隠さない
- 「不労所得」「必ず稼げる」等の文言をコードベースに含めない

ただし **これで規制対象外になると保証するものではありません。** 必ず専門家に確認してください。

### 1.2 日本で確認すべき法令

| 法令 | 論点 |
|---|---|
| **資金決済法** | 暗号資産交換業に該当するか。ユーザーの BTC を「管理」する行為（カストディ）は該当しうる |
| **金融商品取引法** | 集団投資スキーム持分（ファンド）に該当するか。第二種金融商品取引業の登録要否 |
| **出資法** | 元本保証をうたうと出資金受入制限に抵触する |
| **犯罪収益移転防止法（犯収法）** | 特定事業者に該当する場合、取引時確認（KYC）・疑わしい取引の届出が義務 |
| **特定商取引法** | 通信販売としての表示義務（事業者名・所在地・連絡先・返品条件等） |
| **景品表示法** | 収益に関する優良誤認・有利誤認表示の禁止（「必ず儲かる」は明確にアウト） |
| **消費者契約法** | 不当条項・断定的判断の提供の禁止 |
| **個人情報保護法** | KYC 情報の取得・保管・第三者提供・越境移転 |
| **電気通信事業法** | 該当性の確認（外部送信規律を含む） |
| **法人税法・所得税法** | 暗号資産の期末評価・ユーザーの課税関係の案内 |

**特に重要**: ユーザーの BTC 残高を事業者が預かる形（本システムの `wallet_accounts`）は、
日本では **暗号資産交換業（カストディ業務）に該当する可能性が高い**論点です。
回避策としては以下が検討されますが、いずれも専門家の判断が必要です。

1. ユーザー自身のウォレットへ**直接**プールから支払わせ、事業者は一切預からない
2. 登録済みの暗号資産交換業者と提携し、預かりはその業者が行う
3. 自ら暗号資産交換業の登録を取得する

### 1.3 海外展開時

| 地域 | 主な確認先・観点 |
|---|---|
| 米国 | SEC（Howey テストによる証券該当性）、FinCEN（MSB 登録）、州の Money Transmitter License |
| EU | MiCA（暗号資産市場規則）、AMLD |
| シンガポール | MAS、Payment Services Act |
| 香港 | SFC、VASP ライセンス |
| その他 | 中国・アルジェリア等、マイニングや暗号資産取引を禁止・制限する国がある |

**推奨**: 提供国を許可リスト方式で明示的に絞り、それ以外からのアクセスは登録を拒否する。
（本システムは `tenant_settings.feature_flags` で国別制限を実装できる構造にしてあります。）

## 2. AML / CFT（マネーロンダリング・テロ資金供与対策）

| 項目 | 要件 | 本システムの対応 |
|---|---|---|
| 顧客管理（KYC/CDD） | 本人確認・実質的支配者の確認 | `kyc_records` でステータス管理。出金をゲート |
| 制裁リスト照合 | OFAC・国連・日本の資産凍結リスト | 未実装（商用で必須） |
| PEP スクリーニング | 重要な公的地位を有する者 | 未実装（商用で必須） |
| 継続的モニタリング | 異常取引の検知 | `modules/wallet/risk.ts` でスコアリング |
| 疑わしい取引の届出（STR） | 該当時の当局への届出 | 検知結果を管理画面に表示。届出は人が判断 |
| トラベルルール | 一定額以上の送付時の情報通知 | 未実装（該当する場合は必須） |
| 記録保存 | 取引記録・本人確認記録の保存 | `audit_logs` を7年保持 |
| ブロックチェーン分析 | 送金先アドレスのリスク評価 | 未実装（Chainalysis 等の導入を推奨） |

## 3. 消費者保護・表示

### 3.1 必ず表示すべきもの

- [ ] **リスク開示書**（BTC 価格変動・難易度上昇・半減期・設備故障・事業者リスク・元本毀損の可能性）
- [ ] 収益がすべて **推定値** であり、保証されないこと
- [ ] 手数料の全内訳（プール・プラットフォーム・電力・出金）
- [ ] 契約期間・中途解約条件・返金ポリシー
- [ ] 事業者情報（特商法表記）
- [ ] 利用規約・プライバシーポリシー
- [ ] 苦情・相談窓口
- [ ] 税務上の取り扱いは各自で確認する旨の案内

### 3.2 使ってはいけない表現

```
❌ 「元本保証」「必ず儲かる」「確実に」「リスクなし」
❌ 「不労所得」「寝ているだけで増える」
❌ 「年利 ○○% 確定」
❌ 「ASIC 不要で Bitcoin を生成」（技術的に虚偽）
❌ 過去の実績を将来の収益であるかのように示す表示
❌ 損失の可能性に触れない収益シミュレーション
```

```
✅ 「推定収益（保証ではありません）」
✅ 「難易度・価格の変動により、収益はマイナスになる可能性があります」
✅ 「ハッシュレートの利用契約であり、投資商品ではありません」
```

**実装上の担保**: 収益を返す API は必ず `isEstimate: true` と `disclaimer` を含める仕様にし、
これを外すとテストが失敗するようにしてあります（`tests/revenue-engine.test.ts`）。

## 4. 個人情報・データ保護

| 項目 | 対応 |
|---|---|
| 取得の適法性 | 利用目的の明示・同意取得 |
| 保管 | 暗号化・アクセス制御・保持期間の設定 |
| 第三者提供 | KYC ベンダー・カストディへの提供を規約に明記 |
| 越境移転 | サーバー所在国・移転先国を明示（GDPR / 個情法） |
| 開示・訂正・削除請求 | 手順を用意（`OPERATIONS.md`） |
| 漏洩時 | 個人情報保護委員会への報告・本人通知（原則3〜5日以内の速報） |
| Cookie / 外部送信 | 電気通信事業法の外部送信規律への対応 |
| データ最小化 | **KYC 書類の画像は自社で保持しない**設計を推奨（ベンダーに委譲し結果のみ保持） |

## 5. 環境・ESG（B2B・大企業向けに問われる）

| 論点 | 対応 |
|---|---|
| 電力消費・CO2 排出 | 使用電源の構成（再エネ比率）を開示できるようにする |
| 熱回収 | 提携ファームの取り組みを開示 |
| 立地 | 電力系統への影響・地域との合意 |
| 開示 | 企業顧客からサステナビリティ情報を求められる前提で、プロバイダー契約時に取得しておく |

## 6. 事業開始前チェックリスト

- [ ] 弁護士による事業スキームの適法性レビュー（金商法・資金決済法の該当性判断）
- [ ] 必要なライセンスの特定と取得（または提携）
- [ ] AML/CFT 態勢の整備（規程・責任者・研修・届出体制）
- [ ] 利用規約・プライバシーポリシー・リスク開示書の作成とレビュー
- [ ] 特商法表記の掲載
- [ ] 提供国の許可リストの決定と技術的制限の実装
- [ ] KYC ベンダーの選定と契約
- [ ] カストディの適法性確認（自社で預かるのか、業者に委ねるのか）
- [ ] 税務処理の確認（自社の会計処理・ユーザーへの案内）
- [ ] 保険（サイバー保険・暗号資産カストディ保険）の検討
- [ ] 苦情処理・紛争解決の窓口設置（ADR 含む）
- [ ] 事業撤退時のユーザー資産返還手順の事前定義
- [ ] 広告・LP の表現レビュー（景表法）
- [ ] 外部セキュリティ監査の実施
- [ ] 障害・インシデント時の当局報告フローの整備

## 7. 技術側で守っている「コンプライアンス・バイ・デザイン」

| # | 実装上の担保 | 対応する論点 |
|---|---|---|
| 1 | 収益 API は `isEstimate` と `disclaimer` を必ず返す | 景表法・断定的判断の禁止 |
| 2 | 保証表現をコードベースに含めない（テストで検査可能） | 景表法・金商法 |
| 3 | 出金は KYC ステータスでゲートされる | 犯収法 |
| 4 | 全ての金銭操作が追記専用の監査ログに残る | 記録保存義務 |
| 5 | 異常出金検知のスコアリング | AML 継続モニタリング |
| 6 | 秘密鍵をシステムに保持しない設計 | カストディリスクの低減 |
| 7 | テナント別に機能フラグ（国別制限等）を設定可能 | 提供国の制限 |
| 8 | 個人情報の論理削除＋匿名化の手順 | 削除請求への対応 |
| 9 | データ保持期間の明示とパージジョブ | データ最小化 |
| 10 | 手数料の全内訳を UI と API で開示 | 消費者保護・透明性 |
